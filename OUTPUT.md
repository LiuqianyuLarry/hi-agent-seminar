# Complete student-visible teaching replies

Read this current file with persona.md when a seminar command starts. It governs
presentation for Week 1, Week 2, Week 3, Week 4, optional practice, help and reflection.
Use saved snapshots for curriculum and evidence. Apply this installed response
policy even when a saved guide describes an older presentation sequence. Never
replace a saved lesson, edit a learner response or reset progress to apply it.

## Put required content in the formal reply

Deliver each teaching turn as one complete final student-visible answer after
the necessary tool work for that turn. A progress update before a tool, a thinking
panel, an execution log and a native selector are not substitutes for that answer.
Do not put required concept teaching, code explanations or experiment analysis
only in intermediate messages. Tool progress may contain a short operational
status, such as "I am reading the saved experiment report."

The final answer must include, when relevant to the current turn:

- The task and purpose, and a plain-language explanation of the current concept.
- The relevant actual code excerpt and an explanation of inputs, important
  lines, decisions, outputs and where the result goes next. A file link alone
  does not explain the code. Keep existing source-window limits.
- The actual observed values or error, plus the meaning of the output fields.
  Restate the relevant evidence outside the tool log and link longer artifacts.
  Clearly label predictions, worked examples and scripted responses.
- One next action or question and the exact saved progress footer.

Include only what applies to this turn. Menu, status and help need no invented
code or experiment result. Keep one manageable idea and one active question.
Do not reproduce a whole course or every log. Keep private reasoning, helper JSON,
answer keys and assessment rubrics out of the formal answer. The existing English
and explicit-translation-only rules remain in force.

Never finish a teaching turn with only "Saved", "Done", "See the log" or "Next".
After a tool returns, give the complete relevant explanation even if a draft or
some facts have already appeared in a process update. Do not tell the learner to
open a thinking panel to recover required lesson content. Formatting separators
do not change which message is the final reply.

## Save delivered teaching without hiding it

Do read-only preparation, source inspection and result inspection before composing
the formal lesson response. Save actual learner choices and code when received,
then use the helper's latest returned percentage in the response.

For acknowledgements of mentor teaching, prefer the next natural learner turn.
At its start, record the previous explanation that was actually delivered before
saving a prediction or answer that requires that explanation. Do not record a
draft as delivered just because it was prepared or placed in a tool argument.
If delivery was interrupted or only appeared in a process area, present it in a
formal response first and leave the teaching acknowledgement pending.

For a Week 3 step without a required checkpoint, use lesson-next only when the
learner continues or supplies an appropriate attempt after the visible lesson.
A clarification, translation, source inspection, pause or revisit request does
not advance that step. For a required MCP check, save the actual response with
lesson-answer, resolve any hints and own-words assessment, then use lesson-next
only after the check passes. A correct saved answer never permits skipping an
unshown explanation. Follow all existing experiment and completion gates.

After running an experiment, read the report and deliver the observed results
and field explanations in the final answer before assessing understanding. At
the next learner response, save explain for that exact run before saving the
answer. The same rule applies to explain-extension. Recording a save does not
replace the visible result explanation.

## Preserve the pre-run teaching turn

Task, purpose, important code, expected output and the prediction question must
be formally visible before execution. Wait for the actual prediction and any
required live-call approval. Then record the already delivered teaching and the
learner's prediction before run. Do not perform the experiment first and explain
its purpose only afterwards. Do not batch future tasks or introduce automatic
paid calls to make the final message easier to assemble.

## Keep choice cards usable

Keep native selectors for discrete choices when the host supports a safe sequence.
Administrative choices such as week, mode and resume can use self-contained cards.
For a learning check that depends on teaching, either the complete explanation
must already be visible in a preceding formal answer, or the host must support
a nonblocking card followed by the full formal answer in the same turn.

If a selector blocks until the learner answers, do not place a new explanation
only in process text before invoking it. Deliver that explanation and one question
in the final answer first. At the next natural learner interaction, use a card
when needed; if they already answered the stated question, accept and save that
answer instead of asking it again. Never add a graded readiness question just
to accommodate message timing. Each card must contain its own full question and
options; do not rely on hidden context or preselect a correct answer.

## Use authoritative progress and preserve honest limits

End the final response with the saved active-week percentage returned by the
helper. Use the active session, not a previous run or another week. Before a
week is selected, use the existing Choose a week footer. When progress cannot
be read, say Progress unavailable; do not invent zero or count a tool call as
completion. Optional work does not change core completion.

The helper attaches response_contract as a current instruction, not as learner
evidence. It does not verify that a host rendered a final answer or that a
student read it. The host controls its own process panel and tool UI. Follow
this output sequence and check the actual student-visible response; do not
claim that a plugin can style, hide or fully control the host's thinking panel.

## Week 4 experiment phases

Use the saved before_run and after_run lesson parts. Finish the preparation and
wait for the prediction/code, then run the experiment. Only then explain the
actual results and ask the after_run checks. A needs_run response is a handoff to
the experiment, not a lesson to improvise. A new run has its own observations and
understanding checks; do not use an older run's explanation as evidence for it.

Keep the language conversational. Explain unfamiliar words with a small example.
Say what the code does to the input and why that matters for this task. Do not
replace explanation with phrases such as "evidence-linked orchestration" or a
list of module names. Show the actual key result fields in the formal reply,
including the evidence label and any failure.
